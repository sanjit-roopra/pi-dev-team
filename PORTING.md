# Porting dev-team (Claude Code) to pi

Upstream: `bdfinst/agentic-dev-team`, plugin `plugins/dev-team` v14.0.0 (commit 2bf3d98, 2026-09-30).
Target: pi coding agent 1.x (`@earendil-works/pi-coding-agent`; autocompact needs its `agent_settled` event).

## 1. What upstream is

`dev-team` is a Claude Code plugin made of five kinds of parts (upstream counts; the port drops a few skills and adds two agents, see section 4 and the README):

| Part | Count | What it relies on in Claude Code |
|---|---|---|
| Agents (`agents/*.md`) | 46 | `Agent`/`Task` tool with `subagent_type`, frontmatter `model: opus/sonnet/haiku`, `effort`, `tools`, `skills` |
| Skills (`skills/*/SKILL.md`) | 99 (96 user-invocable) | Slash commands, `$ARGUMENTS`/`$0` substitution, `Skill` tool for chaining, `AskUserQuestion`, `allowed-tools` |
| Hooks (`hooks/*.py`, `hooks.json`) | 42 wired | PreToolUse / PostToolUse / SessionStart / Stop / SubagentStop / SessionEnd / UserPromptSubmit, JSON on stdin, exit 2 = block |
| Scripts, libs, tools | ~135 Python files | `${CLAUDE_PLUGIN_ROOT}`, `.claude/` project state, 6 call sites of `claude -p` |
| Knowledge, templates | ~135 files | Plain markdown and JSON, referenced by path |

Many guarantees in the skills are only true because a hook enforces them: careful/freeze/guard, tests-frozen during REFACTOR, the verify loop guard, the `gh pr create` review gate, the review-verdict ledger, cost metering.

## 2. Porting strategy: a compatibility runtime, not a rewrite

Rewriting 99 skills and 46 agents by hand would fork the content and make every upstream release a manual merge. Instead the port ships the upstream content almost unchanged and adds a pi extension that provides the Claude Code runtime contract that content expects.

```
upstream plugins/dev-team  --sync/sync_upstream.py-->  pi-dev-team package
                                                      + extensions/dev-team (TypeScript runtime)
                                                      + extensions/spend (cost views; also loads alone)
                                                      + bin/claude (CLI shim -> pi)
                                                      + overrides/ (pi-specific skills, agents, hooks)
```

`sync/sync_upstream.py` is re-runnable. A new upstream release is one command, and the diff shows only upstream changes plus the small, listed patch set.

### Tools the extension adds

The model uses dev-team through four tools:

| Tool | Claude Code equivalent | Notes |
|---|---|---|
| `dev_team_subagent` | Agent / Task | Runs the agent in a child `pi` process with its own context, tools and tier model. Single calls, parallel calls (several calls in one message, or `tasks[]`), and `isolation: "worktree"`. Accepts `subagent_type`/`prompt` too. Live per-agent progress in the TUI; child spend counts in pi's session totals. |
| `skill` | Skill | Loads a skill with arguments substituted. This is how skills chain (`/specs` → `/plan`, `/ship` → everything). |
| `ask_user` | AskUserQuestion | The human gates, in plain language (`lib/plain-questions.ts`). `w` or `answerMode: wait` stops the timeout. Non-interactive runs take the documented default. |
| `web_fetch` | WebFetch | URL to text. |
| `dev_team_brief` | none (port) | A plain request's brief before its first file change; `tool_call` blocks writes until it (`lib/brief.ts`, `routing`). |

The dispatch tool is `dev_team_subagent`, not `subagent`, so the package coexists with `pi-subagents`.

## 4. What is dropped, and why

| Upstream | Reason |
|---|---|
| Skills `agent-audit`, `agent-eval`, `harness-e2e-check`, `long-eval`, `orchestration-benchmark`, `claude-setup-review` | Test or audit Claude Code's own harness and plugin layout. The agent files `claude-setup-review` and `session-analysis` still ship (byte-identical to upstream) but nothing in the port dispatches them |
| Skill `session-review` | Mines `~/.claude/projects` transcripts. A pi session backend for `session_log` is future work |
| Hook `mcp_json_repowise_nudge` | About Claude's `.mcp.json` |
| Hooks `code_intelligence_nudge`, `code_intelligence_turn_mark`, `phase_marker` | Need Claude transcript turn structure; nudges only. Off by default, can be re-enabled |
| Monorepo-only hooks (`contract_version_guard`, `pre_commit_knowledge_index`, `knowledge_index`, `skills_index`, both banned-script scanners, `eval_compliance_check`) | Only act inside the upstream repo itself. Shipped but disabled by default |

`devtools/pi_session_report.py` is a separate, maintainer-only reader for pi session logs (debugging a run, measuring which skill steps ran). Its `code` subcommand also runs a read-only `git log` in each session's recorded cwd. It is not a `session_log` backend and does not feed `session-review`. It lives outside the managed directories, so the sync never touches it, and it is not in the npm package. The `debug-pi-session` skill in `.agents/skills/` (linked into `.claude/skills/`) is likewise port-owned and dev-only.

## 5. Known differences

- Hook output. In Claude Code, text a PreToolUse/PostToolUse hook prints with exit 0 is only shown in the transcript view. The plugin was written as if the model sees it. The port appends it to the tool result so the model does see it (`hookOutputToModel`, default on).
- Parallel tool calls. Claude Code runs several `Agent` calls in one message in parallel; so does pi. The `dev_team_subagent` tool also accepts `tasks[]`. A global limit (`maxParallelAgents`, default 6; a project file may set 1 to 16) applies across both.
- Subagent transcripts are not saved as sessions (`--no-session`). Usage is captured from the JSON event stream and recorded.
- `allowed-tools` in skills is advisory in pi (as in upstream under `bypassPermissions`).
- Autocompact timing. Claude Code compacts at `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE` between any two turns. The port compacts at that percentage when an agent run ends, because `ctx.compact()` aborts a running turn; within one long run pi's own threshold applies.
- GitHub text style. The port adds rules for pull request, issue and comment text (`lib/github-style.ts`, with `lib/gh-command.ts` and `lib/shell-scan.ts`: plain English after ASD-STE100 and a skim-first layout). The rules are in the `dev_team` system-prompt section of every session and subagent. In `tool_call`, before the PreToolUse hook bridge, a quote- and heredoc-aware scan finds each `gh pr|issue create|edit|comment` and checks its literal title and body. A breaking call is blocked once with the list of problems; the identical resend goes on to the hooks, so `pre_pr_review` still applies (`githubStyle`: `block`, `warn`, `off`; `off` also drops the rules from the prompt). Notes on `/pr`, `/specs`, `/issues-from-plan`, `/issues-from-assessment` and `/autoship` keep their required sections; `/pr` moves Decisions & Assumptions and the Evidence Bundle into one `<details>` block.
- The orchestrator. In Claude Code the main session is the orchestrator the skills describe (`/code-review` opens with "Role: orchestrator"). A pi model read that as "dispatch the `orchestrator` agent", which has no bash or write, so `/code-review` stopped before staging anything. The dev-team guide in the system prompt says the orchestrator is the user's session, that skills which run commands or write files run there, that an agent is dispatched only when its `tools:` cover the work (project agents first), and that a dispatched agent does not start `/code-review`, `/build`, `/pr`, `/ship` or `/fix` unless its task or its own agent instructions say to.
- `/code-review` is a slim core. Upstream's `SKILL.md` is about 102 KB (25k tokens), and in recorded sessions it stayed in context for a median of 57 turns per load, while some of its sections never ran (the opt-in context pack, the dispatch-failure retry). The port ships a short core that keeps every command but `dispatch_waves.py` (one call sends all lenses), the MUST rules word for word, and every phrase upstream's own content tests pin, and moves the full upstream text into `skills/code-review/references/`, split by step. A table at the top of the core names each reference and when to read it; four reads are required (the documentation-only short-circuit, the opt-in context pack, the dispatch-failure retry when `dispatch_reconcile.py` reports a missing agent, and the fix loop before its first iteration), and the core says not to read references otherwise. Three sentences in the upstream text still say step 9 never runs under `--json`, which upstream's own step 7 and step 9 contradict; the core names that exception to its "follow the reference" rule. Nothing upstream wrote is dropped: the reference files joined in order rebuild the upstream file byte for byte, which `test/py/test_slim_skills.py` checks against the pinned hash. `sync/split_skill_references.py` regenerates the references for a re-port.
- Sensitive-file guard (`overrides/hooks/pre_tool_guard.py`, `overrides/hooks/guards.json`). Upstream matches every `blocked_paths` pattern against the whole path, so `*secret*` blocks any file under a folder such as `secrets-manager/` and any report named `secret-triage.md`. Its block message says to confirm with the user, but the block is unconditional, and it names `.claude/hooks/guards.json` while the hook reads the plugin's own copy. In practice an agent asked for approval, got it, and stayed blocked. The port checks the path as written and as resolved (so a harmless-named symlink to a blocked file stays blocked), matches a pattern without `/` against the file name only and a pattern with `/` against the end of the path; adds `allowed_paths` (default `*.md`) plus user exceptions in `DEV_TEAM_GUARD_ALLOWED_PATHS`, which only the user's own `~/.pi/agent/dev-team.json` can set (project env is limited to `PROJECT_ENV_SETTINGS`); blocks agent Write/Edit to that file (path normalized, symlinks resolved, `$PI_CODING_AGENT_DIR` honored; bash is not covered); adds `secret/*`, `secrets/*`, `credentials/*` folder patterns (and their dot-prefixed forms) so basename matching keeps those folders blocked; and names the matching pattern, the real config file and the way to add an exception in the block message.
- Build dead-end retry. Upstream `/build` stops for the human as soon as a step's repair loop gives the same failure signature twice. The port's note on `/build` first retries the step once with `software-engineer` one tier up (`haiku` → `sonnet` → `opus`), passing the checkpoint commit ref, the improved tests, the remaining failure signature and the fixes already tried; only a second dead-end stops. It skips the retry when the step had no tier or the Agent tiers line shows the same model for both tiers (every tier is `inherit` by default). So that the session can tell, its dev-team guide has an "Agent tiers" line with the model each tier resolves to (left out of dispatched agents' guides, which keeps their shared cached prefix free of the session model), and a single dispatch's result ends with `[model <provider/id>, tier <tier>]`, as each section of a parallel result already did. Tier names outside opus/sonnet/haiku/fable and values that are not model ids in pi's catalog (a project's config can set them) reach neither the guide nor the result note.
- Single dispatch results end with a `[model <provider/id>, tier <tier>]` note (parallel results name it in each section heading), so the session and the `/build` retry note know the model a step ran on. A review agent's JSON output is then followed by that line; `validate_review_output.py` still recovers the JSON, but counts it as `prose-preamble` instead of `clean`.
- Lean production code. Upstream's team tends to write more code than a task needs, and its review loop grows it: most lenses propose adding structure, none proposes taking code away. The port changes that for production code only; test scope stays with the Gherkin scenarios. `software-engineer` walks a reuse ladder before writing (does it need to exist? does the codebase, the standard library, the platform or an installed dependency already do it? then the minimum), with "fewer lines, never denser lines", `shortcut:` comments for deliberate debt and a closing `Skipped:` line. `refactor-opportunity-review` is rewritten as a deletion-only simplify lens; it keeps its name and `Scope: on-demand`, so its one dispatch per slice at `/build`'s checkpoint and every file that names it stay as they are, but upstream text that describes it as an extraction lens (`knowledge/agent-registry.md`, `agents/js-fp-review.md`'s deferral, `/build` sub-step 6's "duplication" wording) is now stale; extraction and duplication belong to `structure-review`. `structure-review` applies the rule of three and injects only what the blocker table in `knowledge/internal-collaborator-doubling.md` allows doubling. One lean fix rule (`LEAN_FIX_RULE`, in `structure-review`, `quality-reviewer` and the code-review core, where it is the core's second exception to "follow the reference") makes a restructuring `warning` that grows production code a report-only suggestion. `plan-review-strategic` checks that each step names its reuse and proposes one cut; notes on `/build` and `/plan` carry the same rules. Only the simplify lens is a whole-file override; the other edits are anchored `LEAN_PATCHES`, so upstream changes elsewhere in those agents still flow through. `/code-review`'s per-diff panel has no deletion lens: speculative and reinvented code is caught at `/build`'s slice checkpoint only.
- The request as the spec. Upstream `/plan` with no spec artifact writes its own acceptance criteria and Gherkin, and every later gate (plan critics, `spec-compliance-review`, the build's runtime check) checks against them. A requirement the plan rewords, such as an exact output format, then passes every review. The port's `/plan`, `/specs` and `/ship` commands save the text after the command word for word to `.claude/memory/requests/` (`lib/skills.ts` `saveRequest`), but only when it holds words beyond flags, issue numbers, URLs and paths (`hasRequestText`): `/ship 123`, `/ship --issues 4,5` or `/specs docs/spec.md` point at a request that lives elsewhere, and a saved bare reference would outrank the issue body or document. The `/ship` note passes the path to its `/specs` and `/plan` calls (with no saved file the issue body is the request, as upstream), and the `/specs` note records it in the spec, from which `/plan` copies it. The directory is not git-ignored by the extension: `/setup` step 11 already ignores `.claude/memory/` in user projects, together with the plans that name the file, and an extension that edits a user's `.gitignore` on every command would be a side effect nobody asked for. Code writes it, so a model that shortens the text or invokes the skill again with a summary cannot replace it. The `/plan` note makes that file the spec artifact and copies the request's output examples into the Gherkin unchanged; the `/build` note passes it to `spec-compliance-review` and diffs the request's examples at sub-step 4.9; one `PATCHES` entry on `agents/spec-compliance-review.md` makes a difference from those examples an unmet criterion. An unclear point is an open question, not a decision. In a SlopCodeBench `file_backup` run on Sol, the plan settled two unclear points wrongly as criteria and every reviewer honoured them. In the Opus run, the plan chose the right reading for one of them and listed the doubt, but `spec-compliance-review` at the build's acceptance-criteria gate (already told that the request outranks the plan) read a sort rule and "for each" wording as the other reading, and the build switched to it. Both failures are a guess presented as settled: once by the plan, once by a reviewer. So the `/plan` note cites an example only when its output differs between the readings (it computes both), otherwise falls back to the reading under which every input the request defines changes some output, lists the other reading under `## Risks & Open Questions`, never marks the choice "Plan decision", and asks the question at the interactive approval gate. A second `PATCHES` entry has `spec-compliance-review` check those open choices even when the dispatch calls them settled, but report an `error` only on explicit evidence (an example that separates the readings, or a sentence that states the behaviour); a reading inferred from wording is a `suggestion`, which the build checkpoint loop logs and does not chase, and answers from the user (Ambiguity Log source `user`, plan approval) are settled. The aim is to stop reviewers overturning points the request does not decide, not to give them more reasons to. The `/build` note changes code only on such an `error` and tells `software-engineer` that the request overrides that plan choice. The `/plan` note also gives each stated observable rule (bound, default, order, count, format) its own Gherkin scenario, which keeps test scope with the scenarios; a rule that depends on an open question is tested only on inputs where all readings agree. This is a guess too: it is not shown to fix the checkpoint 1 window tests until an SCB checkpoint 1 run passes them. The checkpoint 2 `total_size` and pack-boundary failures are not targeted: there the hidden tests contradict the spec's own text and Example 2, so following the examples causes them.
- Review profile (`DEV_TEAM_REVIEW=full|lean`, `lib/review-profile.ts`). Upstream has one review depth. In SlopCodeBench runs the review panels were 47-53% of the dollar cost, the review-fix implementer 13-21% of wall time while review fixes changed no hidden-test result. `full`, the default (unset, empty or `full`), is upstream's flow: the skill text, the guide and every agent prompt are byte for byte what they were, and `npm run sync` output does not change, because nothing lean is written into `skills/` or `agents/`. `lean` adds a "Review profile: lean" section to `/plan`, `/build`, `/code-review` and `/ship` when they expand (from `extensions/dev-team/lean/<skill>.md`, inserted after the pi port notes, or after the title for the code-review core) and one line to the dev-team guide.
