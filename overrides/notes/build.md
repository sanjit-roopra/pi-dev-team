## pi port notes (read first)

**One retry on the next tier up before a dead-end stops the build.** This replaces sub-step 2a's "do not dispatch a third attempt against the unchanged signature" with one retry on the next tier up; the hard stop of 2a and the Escalation section applies after that retry. Use it when a step reaches the failure-signature dead-end, whether your own repair loop finds it or the `software-engineer` step report says so:

1. Commit the dead-end checkpoint exactly as sub-step 2a says. If the step report already names a checkpoint commit, use that one.
2. Find the next tier up from the tier the step ran on: `haiku` → `sonnet` → `opus` (`fable` is never a retry target). The dispatch result names the model and tier the step ran on: `[model <provider/id>, tier <tier>]` in a bracket note after a single dispatch's output, `(<provider/id>, tier <tier>)` in a parallel section's heading. The "Agent tiers" line in the system prompt names the model of each tier.
3. Skip to step 6 when the step has no tier (the note shows only `[model <provider/id>]`, or the step ran in this session, not in a dispatched agent), when it ran on `opus` or `fable`, when the Agent tiers line does not name the next tier's model (it shows `(not a model id)`), or when the Agent tiers line shows the same model for the step's tier and the next tier (compare those two entries, not the `[model …]` note, whose id the child reports and may be spelled differently). With the default config every tier is `inherit`, so all tiers are the same model and there is no retry.
4. Dispatch `software-engineer` once more for the same step with `model: "<next tier>"`, in the same working tree (for a worktree slice, set `cwd` to that worktree; do not make a new one). Give it the step, its Gherkin scenario(s), the checkpoint commit ref, the improved tests, the remaining failure signature, and a short list of the fixes already tried, and tell it not to repeat them. Its repair loop uses the same dead-end rule.
5. If the retry reaches green, continue the step normally (REFACTOR, self-verification, review checkpoint). The step report says "retried on `<tier>` (`<model>`) after a dead-end at `<checkpoint commit ref>`", so `/pr` lists it under Decisions & Assumptions.
6. If the retry also dead-ends, or step 3 skipped it, do the hard stop of sub-step 2a and the Escalation section unchanged. When the retry ran, name both dispatches (tier, model, checkpoint commit ref) and count the failed fix attempts (repair iterations) of both toward the "3+ failed fix attempts" rule.

- Retry at most once per step. Never chain it (`haiku` → `sonnet` → `opus`), and never let it reset or raise an iteration cap, for example the review loop's 5 iterations.
- Non-interactive runs (`--yes`, `DEV_TEAM_AUTO_APPROVE=1`, `/ship`, `/autoship`) do the same. The retry is automatic, not a human gate, so it runs before the escalation file is written.
- The retry applies only to the failure-signature dead-end. Every other Escalation condition stops as written.

**Lean production code.** At sub-step 6, `refactor-opportunity-review` is the simplify lens: it only deletes, inlines or replaces production code, and its `error` findings (mechanical removals) fail the lens so the fix loop applies them. Block-to-block duplication now belongs to `structure-review`, whatever sub-step 6 says; replacing a re-implementation with an existing function stays with this lens. In every checkpoint fix loop, the lean fix rule in `agents/quality-reviewer.md` step 4 overrides the actionability table in `knowledge/three-phase-workflow.md` § Review Loop. Test files are exempt.
