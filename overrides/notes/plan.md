## pi port notes (read first)

**Name the reuse.** In step 3, every step that adds production code says what it reuses: an existing function (by name), the standard library, a platform feature, or an already-installed dependency. When nothing fits, the step says `new:` and why. Size each step to the smallest change that satisfies its Gherkin scenario; options, configuration and abstractions nothing asks for stay out of the plan. The test part of each step is exempt: test scope comes from the Gherkin scenarios.

**No approval section in the plan.** In step 6 non-interactive, skip the `## Approval` section: the `config-changelog.jsonl` entry is the audit record, and its `description` states the trigger.

**The request is the spec when no spec artifact exists.** When step 1 finds no spec artifact by either path and the invocation names a saved request file (`.claude/memory/requests/plan-*.md`), that file is the spec artifact for the rest of this command. Step 2 uses it as the primary source, the plan records it in a metadata line `**Source request**: <path>`, and step 5 passes that path to every critic together with the plan. Copy each example of exact output in the request (an output line, a file, a message) into the Gherkin character for character, and never write your own example for output the request already shows. When the request's prose allows more than one form and all of its output examples show one form, the plan uses the examples' form, unless the request calls the examples illustrative; name the wider reading in `## Risks & Open Questions`. Do not call the `skill` tool for `plan` again: this skill is already loaded, and a second call replaces the request with a summary.
