## Review profile: lean (read first)

This session runs the lean review profile, the default (the user did not set `DEV_TEAM_REVIEW=full`). This section overrides the steps below, and the pi port notes above, where they differ. Everything it does not name runs as written: the step 3 `spec-compliance-review` gate, the static self-heal pass (the build-time lint, format and type-check lanes, such as `ruff` and `mypy`, and the project's own), `spec-compliance-review` and `correctness-review` at every checkpoint, the per-step lint and type-check self-verification, runtime verification (4.9), invariants (4.10), the step 5 full-suite run and, when `DEV_TEAM_FARLEY=on`, the step 7 Farley Score (item 6). The static self-heal pass does not run `lizard`; item 4 adds it.

1. **One implementer dispatch per slice.** Dispatch `software-engineer` once per slice, not once per step. Point it at every step of the slice in order; it reads the steps, the slice's Gherkin scenarios and the criteria from the plan file itself, runs the per-behavior cycle for each step in turn and reports each step. Add this line to the task: `Review profile: lean. This overrides the per-behavior cycle's "Run the full test suite" gate, its one-behavior batches and your per-step self-verification. Work one step at a time: implement the whole step, write its tests, then run only that step's tests and paste the run. Refactor once per step, after that green run: when the refactor changes nothing, say so in one line, write no refactor phase marker and do not re-run the tests; when it changes code, re-run the step's tests once. Run lint, type-check and the lizard complexity check once per slice, on the files the slice changed, in the same bash call as the full suite, and fix every lizard threshold breach before you report; run the full test suite once, after the slice's last step, and paste that run in your report. Chain each build_phase.py marker with && onto a neighbouring bash call; never spend a turn on a marker alone. Commit once per slice, after the final full-suite run. Test budget: one test per Gherkin scenario of the step, plus one per rule the request states that no scenario covers; add a case to an existing test's table rather than a new test where you can. Do not write tests for internal helpers, resource or memory bounds (tracemalloc, RSS, open-file counts), signals or KeyboardInterrupt, injected filesystem failures (fsync, rename, inode, permission) or exhaustive permutation matrices, unless the request asks for that behavior.` Mark each step done (sub-step 5) from that report. The dead-end retry in the port notes applies to this dispatch: retry once on the next tier up, from the step that dead-ended.
2. **One review panel per slice.** `trivial` and `standard` steps both defer review to the sub-step 6 slice checkpoint, which runs whenever the slice changed a file that no `complex`-step checkpoint already cleared; `complex` steps keep their sub-step 4 review. Skip the abort check (#2168): dispatch every selected lens at once.
   - **Three lenses, plus security when selected.** At every checkpoint dispatch only `spec-compliance-review` and `correctness-review`. At the build's last slice checkpoint also dispatch `refactor-opportunity-review` (the deletion-only simplify lens) over every production file this build changed, and `security-review` when the resolver selected it for any changed file. Dispatch no other lens: in measured runs the others (structure, test, test-smell, naming, arch, domain, doc, performance, concurrency) found almost no errors, and lean fixes only errors; the complexity pre-pass (item 4) covers what `structure-review` measures. Record the lenses you did not dispatch in the checkpoint record as `skipped (lean profile)`.
   - **Give every lens the diff.** Lenses have no shell and cannot run `git diff`. Before dispatching, write the checkpoint's scoped diff with one bash call (`git diff <checkpoint base> -- <files> > .claude/memory/reviews/diff-<slice>.patch`, the base being the commit the checkpoint reviews from) and name that path in every lens task, so no lens reports that it could not see the change.
3. **Fix only errors, in one round.** At sub-steps 4 and 6, fix only `error` findings; record `warning` and `suggestion` findings in the checkpoint record and the build report, and do not fix them. A lint, type-check or complexity failure from the static self-heal pass or the complexity pre-pass (item 4) is an error and is fixed. Run one fix round: apply the error fixes (one `software-engineer` dispatch with every error, or yourself for a mechanical edit), then run the slice's tests, the lint and type-check tools and the complexity pre-pass. Do not re-dispatch reviewers to verify, with one exception: when the round fixed a `spec-compliance-review` error, re-dispatch `spec-compliance-review` once in verification mode. Do not start a second round. An error still open after the round goes in the build report as an open finding; it stops the build only when tests or lint are red.
4. **Complexity pre-pass at every checkpoint.** In full mode `lizard` runs only in the step 6 backstop `/code-review` (its step 2b), which lean skips, and `structure-review` leaves function length, cyclomatic complexity and parameter count to it. So at each sub-step 4 and sub-step 6 checkpoint, after the static self-heal pass and before the lenses, run the `/code-review` step 2b complexity and duplication tools over the checkpoint's changed files, as `skills/static-analysis-integration/references/tool-configs.md` says (`lizard --csv <files> | python3 ${CLAUDE_PLUGIN_ROOT}/skills/static-analysis-integration/adapters/lizard-adapter.py`, and `jscpd` the same way when it is installed). Pass the findings to every lens as static-analysis context ("detected by static analysis — do not re-report, focus on semantic concerns"). Every `lizard` threshold breach and `jscpd` clone in a file this build changed is an `error` for item 3. When `lizard` is not installed, say so in the checkpoint record and the build report.
5. **No step 6 backstop.** This build was invoked with `--backstop-review=skip` (see Parse Arguments). The lean profile is the enclosing caller's assertion that flag requires: the user kept the lean default, and the lean slice checkpoints are the enclosing review. First check that every file this build changed was reviewed at a checkpoint (fix-round edits count as reviewed). Run `/code-review --internal` over only the files no checkpoint reviewed, if any. Then print `Step-6 backstop review skipped (--backstop-review=skip) — enclosing reviewer: lean slice checkpoints (DEV_TEAM_REVIEW=lean).` and append the `outcome: "skipped"` row as step 6 says.

Lean has no step 6 panel, so that Farley result stands unless the suite was red or a later fix changed or added a test file; then dispatch it once more after the fix.

7. **Keep the test budget through review.** When you dispatch a fix round, do not pass on a request for tests beyond the item 1 budget, whatever its severity. (`test-review` and `test-smell-review`, when another command dispatches them, get a lean note with the same budget.)
8. **Short dispatch tasks.** Every agent dispatched here can read the plan, the request and the repository. A task names the plan path, the slice and step ids, the files in scope, the diff or findings file to read, and the constraints above; it does not restate the plan's steps, scenarios, acceptance criteria or the authoring digest, and it stays under about 150 words plus the lean line in item 1. A fix-round task lists each error finding as one line (`lens: file:line: what to fix`), not the reviewer's full text. Do not ask an agent for a report file: its final message is its report.
9. **No-op steps when no human is attached.** When `DEV_TEAM_INTERACTIVE` is unset, skip the Feedback & Learning step (no human gave corrections to capture) and say so in one line.
